# Rules of the road for univocity

Solidity contracts for on-chain split-view protection. These are this
repository's load-bearing invariants (`U#`). The platform rules (`P#`) are
in [forestrie/protocol rules/platform.md](https://github.com/forestrie/protocol/blob/main/rules/platform.md);
a rule marked `⤷ specialises P#` is that platform rule's concrete check
here. Agents load a one-line digest of both,
`.claude/rules/rules-of-the-road.md`, generated by `dox digest`. The
contract is the ground truth: an invariant that is not enforced on-chain is
not enforced.

Each rule has **Why**, a source link and **Enforced-by**. Versioning:
MAJOR removes or redefines a rule, MINOR adds one, PATCH rewords.

### U1 — Verify both sealing and authority on-chain in publishCheckpoint
`publishCheckpoint` MUST verify (a) the checkpoint is signed by the log's
root key or a valid delegation of it, and (b) the presented grant's
inclusion in the parent log against the parent's on-chain accumulator,
within the grant's size bounds, link by link to the bootstrap key bound at
deploy. **Why:** this publish-time check is what lets any chain read stand
in for the sealing and authority questions.
⤷ specialises P4, P10. [ARC-0017 auth overview](arc/arc-0017-auth-overview.md)
· [devdocs ADR-0032](https://github.com/forestrie/devdocs/blob/main/adr/adr-0032-delegated-checkpoint-signature-verification.md)
· [receipt trust model §3](https://github.com/forestrie/protocol/blob/main/spec/receipt-trust-model.md#3-authority--is-this-log-authorised-back-to-the-genesis--bootstrap-key).
**Enforced-by:** test:test/checkpoints/Univocity.t.sol, test:test/checkpoints/UnivocityDelegation.t.sol, test:test/checkpoints/UnivocityGrantLonePeak.t.sol, test:test/checkpoints/UnivocityGrantRequirements.t.sol, test:test/checkpoints/UnivocityBounds.t.sol

### U2 — Never gate publishCheckpoint on msg.sender
Anyone holding a valid grant and a signed checkpoint may pay gas to
publish; payer, issuer and submitter are distinct. **Why:** a sender check
would hand an operator a censorship lever the model exists to remove.
⤷ specialises P6. [ADR-0001](adr/adr-0001-payer-attribution-permissionless-submission.md)
· [devdocs ARC-0016 §6.2](https://github.com/forestrie/devdocs/blob/main/arc/arc-0016-checkpoint-incentivisation-model.md#62-permissionless-submission).
**Enforced-by:** test:test/checkpoints/Univocity.t.sol

### U3 — Treat maxHeight as a ceiling, never a balance
Enforce `size ≤ maxHeight` (an entry-count high-water mark) and any
`minGrowth ≤ delta`; do not store or decrement a per-grant balance or
counter. Two grants over one log do not sum; either bound may apply, and
the isolation unit is the log. **Why:** a decrementing balance would make
grants spendable and refundable, breaking irrevocability.
⤷ specialises P8. [devdocs ARC-0028 §2](https://github.com/forestrie/devdocs/blob/main/arc/arc-0028-grant-funded-task-escrow.md).
**Enforced-by:** test:test/checkpoints/UnivocityBounds.t.sol, review

### U4 — Set one root per instance, once, and never reassign it
The bootstrap key is bound once, at deploy, and `rootLogId` is set once,
by the first checkpoint the bootstrap key signs; neither is reassigned.
The root is the account, authority and fee boundary. Production instances
deploy `ImutableUnivocity`, which binds the key in its constructor and has
no upgrade path. `UUPSUnivocity` binds it in a one-shot initializer, and its
upgrade admin can replace the implementation, and with it this rule: on
that variant the upgrade admin is an explicit trust assumption. **Why:**
every downstream guarantee resolves to this single enforced root, and a
reassignable root voids all of them.
⤷ specialises P14. [devdocs ADR-0059](https://github.com/forestrie/devdocs/blob/main/adr/adr-0059-instance-root-fee-accounts.md)
· [devdocs ADR-0034](https://github.com/forestrie/devdocs/blob/main/adr/adr-0034-forest-genesis-chain-binding-required.md)
· [trust boundaries §4.2](https://github.com/forestrie/protocol/blob/main/spec/trust-boundaries-and-operator-powers.md#42-the-upgrade-admin).
**Enforced-by:** test:test/contracts/UUPSUnivocity.t.sol, review

### U5 — Emit one CheckpointPublished per checkpoint as the meter
Emit one `CheckpointPublished` per checkpoint carrying `logId`, kind and
size; the contract keeps no billing counter, and indexers count events.
**Why:** metering is off-chain by counting events, which keeps the contract
minimal and the meter publicly reconstructible.
[devdocs ARC-0026](https://github.com/forestrie/devdocs/blob/main/arc/arc-0026-onboard-grant-apis-and-fee-tracing.md).
**Enforced-by:** test:test/checkpoints/UnivocityStateAndEvents.t.sol, review

### U7 — Verify on-chain COSE/CBOR against the canonical wire bytes
On-chain COSE/CBOR verification MUST match the exact canonical bytes the
sealer signs. **Why:** the contract is the arbiter of "conformant"; any
decode divergence rejects valid receipts or, worse, accepts malformed ones.
⤷ specialises P16. [devdocs ADR-0046](https://github.com/forestrie/devdocs/blob/main/adr/adr-0046-checkpoint-is-consistency-receipt.md).
**Enforced-by:** test:test/cosecbor/cosecbor.t.sol, test:test/checkpoints/TsOnchainDelegationVectors.t.sol, test:test/checkpoints/Kat39ReceiptChains.t.sol, test:test/checkpoints/RealAuthenticatorWebAuthnGolden.t.sol

### U8 — Keep the base contract policy-agnostic over derived flags
The `GF_DERIVED` flag space is reserved for reuse by external protocols.
Native validation ignores derived bits; a composing contract, not the base
one, enforces policy on them. **Why:** keeping the base contract free of
policy is what lets other protocols build on it without forking it.
[devdocs ARC-0029](https://github.com/forestrie/devdocs/blob/main/arc/arc-0029-derived-grant-policy-and-sender-bound-enforcement.md).
**Enforced-by:** review
